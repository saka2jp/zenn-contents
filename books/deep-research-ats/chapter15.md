# ATS（採用管理システム）理解度チェッククイズ

各セクションから2〜3問、合計25問。難易度を基礎・応用・発展で混合。

## エグゼクティブサマリー・市場

### Q1. ATSが解決する最も根本的な課題を説明してください。

:::details 回答
大量の応募書類をメール・スプレッドシートで管理する限界を解消すること。インターネット求人の普及で応募量が爆発的に増加したことにより、従来のアナログ管理が破綻し、候補者データベース・選考パイプライン・評価・通知を一元管理するシステムが必要になった。
:::

### Q2. ATSは「いつ採用すべきでないか」を3つ挙げてください。（設計判断型・基礎）

:::details 回答
1. 年間採用数が数人以下の極小規模組織（コスト対効果が合わない）
2. 採用プロセスを標準化したくない、職人的なハンドオフが中心の採用文化
3. 完全に内製化されたHR技術基盤を持ち、ATSとのAPI統合リソースがない場合

「データロックインリスクを許容できない」も正解。
:::

### Q3. ATS市場でSaaS（クラウド）型が占める割合は何%か。また、その理由を説明してください。（事実確認・応用）

:::details 回答
2025年時点で **88.12%**（出典: Straits Research）。

理由:
- 初期導入コストの低減（オンプレミスと比較）
- 自動アップデートによるメンテナンスコスト削減
- リモートアクセス・モバイル対応の容易さ
- 他SaaSツール（HRIS・評価ツール等）とのAPI連携のしやすさ
:::

## データモデル設計

### Q4. GreenhouseとLeverで「候補者」の主要エンティティが異なります。それぞれを説明し、設計思想の違いを論じてください。（比較型・応用）

:::details 回答
- **Greenhouse**: `Candidate`（人としての存在）と `Application`（ポジションへの応募行為）を分離したモデル。1人の候補者が複数のポジションに応募した場合でも、Candidateは1つで、Applicationが複数紐づく。
- **Lever**: `Opportunity`（候補者×ポジションの組み合わせ）を主要エンティティとして統合。Candidateエンドポイントは2020年廃止。

設計思想の違い:
- Greenhouseは「採用管理」思想（候補者データの正規化を重視）
- LeverはCRM（候補者関係管理）思想で、候補者との接点・経路を機会ベースで追跡することを重視
:::

### Q5. ATSのScorecardエンティティが持つべき属性を設計し、その設計判断の理由を説明してください。（設計判断型・応用）

:::details 回答
必要属性:
- `id`: UUID
- `interview_id`: FK（面接との紐づけ）
- `reviewer_id`: FK（評価者のユーザー）
- `overall_rating`: Enum（STRONG_YES / YES / NO / STRONG_NO）
- `attributes`: AttributeScoreの配列（スキル別評価）
- `private_notes`: Text（他の面接官に非公開のメモ）
- `submitted_at`: DateTime

設計判断の理由:
- `private_notes`を独立させるのは、特定の面接官だけが見られるコメントがあるため（プライバシー・法的リスク配慮）
- `overall_rating`を4段階にするのは「曖昧なYes」を排除するため（Googleも同様の設計）
- `attributes`を配列にするのは、ポジションごとに評価軸が異なるため
:::

### Q6. ATSのJobエンティティに `pipeline_id` を持たせる設計の利点は何ですか？（設計判断型・発展）

:::details 回答
「求人ごとに選考ステージの構成をカスタマイズできる」という利点がある。

例:
- エンジニア職: 書類選考 → コーディングテスト → 技術面接 → カルチャーフィット → 最終面接
- 営業職: 書類選考 → 電話スクリーニング → 商談ロールプレイ → 役員面接

1つの固定パイプラインではなく、職種・チーム・部門ごとに異なるパイプラインを定義することで、採用プロセスの多様性に対応できる。
:::

## API設計

### Q7. Greenhouse Harvest APIが2026年8月にv1/v2を廃止する影響と、移行対応の設計を説明してください。（事実確認・応用）

:::details 回答
Harvest API v1/v2は2026年8月31日廃止予定。v3が現行バージョン（出典: Greenhouse Support）。

影響:
- v1/v2を使ったカスタム統合が動作しなくなる
- パートナー企業の統合ツールも対応が必要

移行対応の設計:
1. 既存のAPI呼び出しをv3エンドポイントに更新
2. v3のレスポンス形式の差分を確認し、パーサーを更新
3. APIバージョンを設定ファイルで管理し、切り替えを容易にする（ハードコードしない）
:::

### Q8. ATSのWebhookを実装する際、「冪等性（Idempotency）」をなぜ確保する必要があるか説明してください。（概念理解型・応用）

:::details 回答
ATSのWebhookは「少なくとも1回（at-least-once）」配信を保証することが多く、ネットワーク障害や再試行により同一イベントが複数回配信される可能性がある。

もし冪等性を確保しないと:
- 候補者のHIRIS登録が重複する
- メール通知が重複送信される
- 給与設定が二重で作成される

対策:
```python
def handle_webhook(event_id: str, payload: dict):
    if ProcessedEvent.exists(event_id):
        return  # 重複処理をスキップ
    with transaction():
        ProcessedEvent.create(event_id)
        process_payload(payload)
```

`event_id`（またはIDempotency Key）を使ってイベントの重複処理を防ぐ。
:::

### Q9. Greenhouse（50req/10sec）とLever（10req/sec）のレート制限の違いを踏まえ、統合システムの設計でどのような対策が必要か説明してください。（設計判断型・発展）

:::details 回答
異なるレート制限への対応設計:

1. **バックオフ付き再試行**
   - 429レスポンスを受けたら指数バックオフで再試行
   - `Retry-After` ヘッダーがあればその時間を尊重

2. **キューベースの非同期処理**
   - 同期的なAPI呼び出しをやめ、ジョブキュー（Celery/SQS）経由で実行
   - キューワーカーがレート制限内でAPI呼び出しを処理

3. **トークンバケット/リーキーバケットアルゴリズム**
   - クライアント側でもリクエスト送信頻度を自律的に制御

4. **バルク操作の活用**
   - 個別更新ではなく、バッチAPIが提供されている場合はバッチを優先

5. **Webhookとポーリングの使い分け**
   - 変更検知にポーリングではなくWebhookを使い、不要なAPIコールを削減
:::

## 標準仕様・連携規格

### Q10. schema.org JobPostingとLinkedIn Job Postings APIは何が違いますか？（比較型・基礎）

:::details 回答
**schema.org JobPosting**:
- 自社キャリアページのHTML/JSONLDに埋め込む構造化データ
- 検索エンジン（特にGoogle for Jobs）が求人ページを理解・インデックスするための標準
- 媒体への「掲載API」ではなく、SEO/クロール向けのセマンティックマークアップ

**LinkedIn Job Postings API**:
- LinkedInプラットフォームに求人を直接投稿・管理するためのREST API
- 認証（OAuth）が必要
- CREATE/UPDATE/CLOSE操作でLinkedIn側のデータを管理する能動的なAPI

両者は目的が異なる: schema.orgは「検索エンジンへの情報提供」、LinkedIn APIは「LinkedIn上への求人配信」。
:::

### Q11. LinkedIn RSC（Recruiter System Connect）の技術的な仕組みを説明してください。（概念理解型・発展）

:::details 回答
RSCは採用担当者がLinkedIn Recruiter画面からATS内の応募状況をリアルタイムで確認できる深い統合機能。

技術的な仕組み:
1. ATSはJob PostingsAPIで求人を投稿する際に `partnerRequisitionId`（ATSのJobID）を送信
2. 候補者がLinkedInから応募すると、ATSのApplication APIへデータが送られる
3. LinkedIn Recruiterのダッシュボードから、ATSのApplicationステータスをAPIで取得して表示
4. `accessRestricted` フラグで、どの採用担当者にATSのデータを見せるかを制御

求人とATSのJob Requisitionを `partnerRequisitionId` で紐づけることが核心設計。
:::

### Q12. JDX（Job Data Exchange）はなぜ必要とされたのか、既存のschema.org JobPostingとの違いを説明してください。（概念理解型・発展）

:::details 回答
schema.org JobPostingは検索エンジン向けのシンプルなフォーマットであり、採用システム間（ATS-HRIS-ジョブボード）の詳細なデータ交換には不十分だった。

JDXが追加する価値:
- **意味論的な精度**: 職務要件・コンピテンシー・キャリアパスをRDFで厳密に定義
- **相互運用性**: HR Open Standards準拠のシステム間でのデータ交換の標準化
- **機械可読性**: スキルマッピング・給与比較・労働市場分析に活用可能な構造化データ

HR Open StandardsとSchema.orgをベースとし、RDFボキャブラリとして実装している点が技術的な差分。
:::

## マルチテナント設計

### Q13. ATSのマルチテナント設計でPool（共有スキーマ）パターンを採用する場合、PostgreSQL Row Level Security（RLS）をどのように活用するか説明してください。（設計判断型・発展）

:::details 回答
RLSはDB層でテナントデータのアクセス制御を行うことで、アプリケーション層のプログラマーミスによるデータリークを防ぐ。

実装:
```sql
-- RLSを有効化
ALTER TABLE applications ENABLE ROW LEVEL SECURITY;

-- テナント分離ポリシー
CREATE POLICY tenant_isolation ON applications
  USING (tenant_id = current_setting('app.current_tenant')::UUID);

-- アプリケーション側でリクエスト処理前にテナントを設定
SET app.current_tenant = 'acme-corp-uuid';
```

RLSの利点:
- アプリ層で `WHERE tenant_id = ?` を書き忘れても、DBが自動的に正しいテナントのデータのみ返す
- パフォーマンスも `tenant_id` インデックスを使って効率的に動作

注意点:
- `SECURITY DEFINER` 関数経由だとRLSがバイパスされる可能性があるため設計注意
:::

### Q14. 大企業テナントと中小企業テナントで異なるデータ分離戦略を採用するハイブリッドアプローチのメリット・デメリットを論じてください。（トレードオフ型・発展）

:::details 回答
**メリット**:
- コスト最適化: 大多数のSMBテナントを低コストの共有DBに収容
- 大企業への対応: エンタープライズ顧客の高いセキュリティ・コンプライアンス要件（SOC2・HIPAA等）に専用DBで応答可能
- スケールの柔軟性: SMBはPool側を横スケール、大企業は専用インスタンスを縦スケール

**デメリット**:
- オペレーション複雑度: 2つの異なるデータベース戦略を同時に運用・監視する必要がある
- テナント移行コスト: SMBが成長してエンタープライズになった際、共有DB→専用DBへのデータ移行が必要
- テスト複雑化: 両パターンに対するテストスイートが必要

**判断基準**: 大企業テナントが全体収益の大部分を占める場合、このハイブリッドアプローチが最も現実的。
:::

## AI/ML機能

### Q15. レジュメパーシングにおいて「スキル表記のゆらぎ」問題とはどういうことか、解決アプローチを説明してください。（概念理解型・応用）

:::details 回答
同一スキルが様々な表記で記載される問題:
- "Python" / "Python 3" / "Python3" / "Py" / "python"
- "AWS" / "Amazon Web Services" / "Amazon AWS"
- "機械学習" / "Machine Learning" / "ML"

解決アプローチ:
1. **スキル辞書（正規化辞書）**: 表記のゆらぎと正規化後のスキル名のマッピングテーブルを作成
2. **文字列類似度**: Levenshtein距離やJaro-Winkler類似度でのファジーマッチング
3. **NERモデル**: 文脈から技術名を認識するモデルを訓練（"I built APIs with Python" → "Python"）
4. **LLMの活用**: GPT/Gemini等のLLMに「このスキルはXですか？」と問い合わせる（精度高・コスト高）
5. **スキルオントロジー**: ESCO（欧州スキル分類）等の業界標準オントロジーを活用
:::

### Q16. ATSのAI候補者スクリーニングにおいて「Amazon 2018年のケース」が与えた教訓を説明し、現在の設計で取るべき対策を論じてください。（設計判断型・発展）

:::details 回答
教訓: Amazonが開発したAI採用ツールが、過去10年の採用データを学習した結果、技術職の採用が男性に偏っていたため「女性候補者に低スコアを付ける」バイアスを習得した。2018年に廃止。

問題の根本: 過去のバイアスを含む採用データで訓練→AIがバイアスを強化・拡大

現在の設計で取るべき対策:
1. **保護属性の除外**: 性別・人種・出身校（間接的に人種と相関する場合）を特徴量から除外
2. **公平性指標の定期評価**: Equal Opportunity / Demographic Parity を定期的にモニタリング
3. **Human in the Loop**: AIスコアは参考指標に留め、最終判断は人間が行う設計
4. **訓練データの多様性検証**: 採用データの保護属性別分布を確認
5. **結果の監査**: 採用されたグループと不合格グループの保護属性分布を定期比較
:::

### Q17. セマンティック類似度（Embeddingベース）とTF-IDFベースのキーワードマッチのトレードオフを比較してください。（トレードオフ型・発展）

:::details 回答
| 比較軸 | TF-IDF | Embedding（BERT等） |
|--------|--------|-------------------|
| 「Python開発者」と「Pythonエンジニア」のマッチ | キーワード不一致でスコア低 | 意味的に近いためスコア高 |
| 計算コスト | 低い | 高い（GPUが望ましい） |
| 説明可能性 | 高（どのキーワードがスコアに寄与したか明確） | 低（ブラックボックス的） |
| ドメイン特有用語 | 事前にキーワード辞書を作れば対応可 | ドメイン固有データでファインチューニングが必要 |
| 多言語対応 | 言語ごとに別途処理が必要 | Multilingual BERTで一定対応可 |

実務での推奨: ハイブリッドスコアリング（TF-IDF × αa + Embedding類似度 × β）で両者の補完が有効。
:::

## システム連携パターン

### Q18. ATSとHRISの統合において、「オファー承諾トリガー」パターンの設計とデータ変換上の課題を説明してください。（設計判断型・応用）

:::details 回答
設計:
```
ATS: Offerステータスが ACCEPTED に変更
  → Webhook発火（offer.accepted イベント）
  → 統合ミドルウェアが受信
  → ATSの候補者データをHRISの従業員エンティティ形式に変換
  → HRISにPOSTして従業員レコード作成
```

データ変換上の課題:
1. **IDの不一致**: ATSの候補者IDとHRISの従業員IDが別体系
2. **項目の欠如**: ATSには在籍するが、HRISには必要な「部門コード（HRIS側固有）」がない
3. **日付形式**: ATSの入社日はISO 8601、HRISはUnixタイムスタンプ、等
4. **オプトインフィールド**: 任意入力だったEEOCデータがHRISで必須の場合
5. **重複防止**: 二重アーカイブでの重複実行防止（冪等性）

対策: マッピング設定ファイルで変換ルールを宣言的に管理し、未マッピングフィールドは警告を出して手動対応できるUIを提供。
:::

### Q19. バックグラウンドチェック（BGC）ツールとATSを連携する際、候補者のプライバシー観点から特に注意すべき設計ポイントは何ですか？（設計判断型・発展）

:::details 回答
1. **候補者の同意管理**: BGCの実施には候補者の明示的な同意が必要（FairCredit Reporting Act / GDPR）。同意取得フローをATS内に組み込み、同意のタイムスタンプを記録

2. **データの最小化原則**: BGCベンダーへ送信するのは調査に必要な最小限のデータのみ（氏名・生年月日・SSN等）。不要な属性（スキル・評価等）は送信しない

3. **BGCステータスの分離**: BGC結果は候補者の採用評価データと分離して保管。採用選考とBGCを混在させると法的リスク

4. **結果の保持期間**: BGCレポートの保持期間は各国法規制を確認し、期限後に自動削除するジョブを実装

5. **FCRA（米国）対応**: 不採用判断の前に「Before Action Notice」を送付し、候補者が反論できる機会を与える手順をワークフローに組み込む
:::

## 設計総合

### Q20. ATSのデータを「忘れられる権利（GDPR Article 17）」に対応するため、どのような技術設計が必要ですか？（設計判断型・発展）

:::details 回答
要件: EU候補者が削除リクエストを送ると、14日以内にすべての個人データを削除する義務

技術設計:
1. **削除APIエンドポイント**
   ```
   DELETE /v1/candidates/{id}?reason=gdpr_erasure
   ```

2. **カスケード削除の設計**
   - Candidate → Applications → Scorecards → Interviews → Notes
   - 関連ドキュメント（S3/GCS の履歴書PDF）も削除
   - 検索インデックス（Elasticsearch）からも削除

3. **匿名化 vs 完全削除**
   - 採用分析の統計目的のみ: 個人識別情報を削除し匿名化データを保持（`candidate_hired = true` 等の集計データ）
   - 履歴書等の文書: 完全削除

4. **削除伝播の非同期処理**
   - Webhookで連携済みの外部システム（HRIS・評価ツール等）にも削除通知を送信

5. **削除ログの保持**
   - 削除したこと自体は記録（個人情報は含まない）
   - 「誰が、いつ、何を理由に削除したか」の監査ログ

6. **バックアップからの削除**
   - バックアップを暗号化し、暗号鍵をテナント・ユーザーごとに管理
   - 鍵を破棄することでバックアップからも実質的に削除
:::

### Q21. Unified API（Merge.dev / Unified.toなど）を採用するケースと自前でATS統合を実装するケースの判断基準を論じてください。（トレードオフ型・応用）

:::details 回答
**Unified API採用が有利なケース**:
- 複数のATSに対応するB2B SaaSを開発している（例: 採用分析SaaS）
- 対応が必要なATSが5社以上ある
- 各ATSのAPIバージョンアップ・廃止への対応コストを避けたい
- 自社の開発リソースがATS統合のメンテナンスに割けない

**自前実装が有利なケース**:
- 対応するATSが1〜2社のみ（追加費用対効果が出ない）
- Unified APIが対応していない機能（スコアカード送信・カスタムフィールド等）が必要
- データをUnified APIベンダーに通過させることのセキュリティリスクが許容できない
- 特定のATSとの深い統合（例: Greenhouse Partner Integration）が必要

**コスト比較観点**:
- Unified API: 月額数百〜数千ドルの利用料 vs 各ATSの統合・保守コスト
- 3社以上のATSを対応させるなら、Unified APIがROI的に有利になるケースが多い
:::

### Q22. マルチリージョン展開するATSが「データレジデンシー（Data Residency）」要件に対応するための設計を説明してください。（設計判断型・発展）

:::details 回答
データレジデンシーとは、特定の地域のデータが法規制によりその地域内のサーバーに保存されなければならない要件（EU GDPRでのEU内保存要件など）。

設計アプローチ:
1. **テナント設定でのリージョン指定**
   ```json
   { "data_residency_region": "eu-west-1" }
   ```

2. **テナントルーティング**
   - テナント識別後、設定されたリージョンのDBに接続をルーティング
   - テナントのホームリージョンを管理するグローバルメタデータDBを別途用意

3. **データ主権の徹底**
   - EU顧客の個人データはEU外のDBには一切複製しない
   - バックアップもEU内のリージョンのみ

4. **分散アーキテクチャ**
   ```
   Global Control Plane（テナントルーティング情報のみ）
     ├── EU Region: EU顧客のデータ
     ├── US Region: US顧客のデータ
     └── APAC Region: APAC顧客のデータ
   ```

5. **監査ログの地域別保持**
   - EUデータへのアクセスログもEU内に保持

課題: クロスリージョンレポーティング（複数拠点を持つ企業の全社採用分析）が困難になる。匿名化集計データのみを集約する設計で対応。
:::

## 発展問題

### Q23. ATS APIのバージョン管理で「URIバージョニング（/v1/, /v2/）」と「ヘッダーバージョニング（API-Version: 2024-01-01）」のトレードオフを論じてください。（トレードオフ型・発展）

:::details 回答
**URIバージョニング（/v1/, /v2/）**:
- 利点: ブラウザから直接テスト可能・キャッシュしやすい・視覚的にわかりやすい
- 欠点: エンドポイントの重複・URLが変わるため既存の統合を壊す

**ヘッダーバージョニング（LinkedIn方式: LinkedIn-Version: 202503）**:
- 利点: URLを変えずにバージョン切り替え可能・REST的に「同一リソースへのアクセス」という原則に沿う
- 欠点: ブラウザから直接テストしにくい・ヘッダーを忘れやすい

**実際のATSの選択**:
- Greenhouse: URIベース（/v1/、将来の廃止時はURL変更を明示）
- LinkedIn: ヘッダーベース（`LinkedIn-Version: 202503`）

**推奨**: 外部パブリックAPIにはURIバージョニングが多い（発見可能性が高い）。内部APIや厳密にクライアントを管理できる場合はヘッダーバージョニングが保守しやすい。
:::

### Q24. ATSのレジュメパーシングでLLM（GPT-4等）を使う場合のメリット・リスク・コスト設計を論じてください。（トレードオフ型・発展）

:::details 回答
**メリット**:
- 多様なフォーマット・言語に対応可能（英語・日本語・中国語等を統一処理）
- セクション識別の精度が高い（箇条書き・表形式・自由文等の多様な構造に対応）
- プロンプトエンジニアリングで出力形式を柔軟に制御できる

**リスク**:
- **個人情報をAPIへ送信**: 候補者の個人情報をOpenAI/Google等のAPI送信する場合、GDPR/CCPAの観点からデータ処理契約（DPA）締結が必要
- **幻覚（Hallucination）**: LLMが実際にないスキルや経験を生成する可能性
- **一貫性の欠如**: 同じレジュメでも毎回異なる出力が返ることがある

**コスト設計**:
- トークン消費コストが高いため、まず安価なNER+ルールベースで処理し、解析失敗時のフォールバックにLLMを使う2段階設計が現実的
- ローカルLLM（LLaMA等）の活用で個人情報問題とコスト問題を同時解決（精度はやや低下）

**実装例（2段階）**:
1. spaCy NER + ルールで処理（90%ケースをカバー）
2. 信頼スコア低の場合のみGPT-4でリトライ（残り10%）
:::

### Q25. ATSを0から設計する場合、最初に決めるべき最重要の技術的設計判断を3つ挙げ、その理由を説明してください。（設計判断型・発展）

:::details 回答
**1位: マルチテナント戦略（Pool/Bridge/Silo）**

理由: 後から変更が最もコストのかかる決断。データモデル設計・パフォーマンス・セキュリティ・コンプライアンス対応すべてに影響する基盤的な選択。スタートアップなら共有スキーマ+RLSから始め、エンタープライズ顧客向けに必要に応じてSiloに移行できる設計にする。

**2位: イベント駆動アーキテクチャの採用（Webhook/イベントバス）**

理由: ATSは多数の外部システム（HRIS・評価ツール・BGC・コミュニケーションツール）と連携する宿命がある。同期的な点対点連携ではなく、イベントバス（Kafka/SNS等）経由のパブサブパターンにすることで、新しい連携先を追加してもコアシステムを変更せずに済む。後からイベント駆動に移行するコストは膨大。

**3位: 候補者データモデルの設計（Candidate分離 vs Opportunity統合）**

理由: Greenhouse方式（Candidate+Application分離）とLever方式（Opportunity統合）のどちらを選ぶかにより、UI設計・API設計・データ集計方法が大きく変わる。「1人の候補者が複数ポジションに応募できるか」「CRM的な視点で候補者との関係を管理したいか」で方針が決まる。
:::
